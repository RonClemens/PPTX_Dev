# PPTX Review AI Assistant

A webapp that ingests a `.pptx` file (with or without PowerPoint comments),
lets a human and an AI digital assistant review and adjudicate it -- every
AI action recorded as a threaded comment reply, every text edit recorded as
a resolved "Edited text" note -- and exports an updated `.pptx`. Along the
way, the deck's content (including tables) is projected into a JSON model
and per-slide, CriticMarkup-annotated Markdown for storage and for the AI's
context.

This is the PowerPoint counterpart of the DOCX Track-Changes AI Assistant:
same workflow (Review / Adjudicate modes, AI Review, Comment Resolution
Matrix with TSV export and XLSX round trip, per-comment AI chat, JSON-file
persistence, Render/GovCloud deployment), rebuilt on a `.pptx` engine and a
slide-based UI.

## Quick start (browser test)

```bash
# Backend (serves the built frontend too when PPTX_DEV_FRONTEND_DIST is set)
cd frontend && npm install && npm run build && cd ..
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
PPTX_DEV_FRONTEND_DIST=../frontend/dist .venv/bin/uvicorn app.main:app --port 8000
# open http://localhost:8000, enter a name, and upload samples/sample.pptx
```

`samples/sample.pptx` is a small 4-slide deck (title slide, bullets with a
requirement ID, a table, a picture, speaker notes) carrying four real
PowerPoint-format comments, including a threaded reply and a whole-slide
comment -- enough to try every feature without any other file. It is
regenerated by `backend/tests/fixtures/make_sample.py`.

## What's different from Word

PowerPoint has **no Track Changes**, and its comments are not anchored to
text. Three consequences shape this app:

| Word version | PowerPoint version |
| --- | --- |
| Edits are real tracked `w:ins`/`w:del`; accept/reject per change | Text is edited **in place**. Each edit leaves an automatic, already-resolved comment on the shape reading `Edited text: "old" -> "new"` (authored by the editor), so the before/after stays visible inside the `.pptx` itself (PowerPoint's Comments pane) and in the app's "Text edits" list. No accept/reject UI. |
| Comments anchor to an exact text span | A comment attaches to a **slide position**. The app maps that to the **shape** it sits in (smallest containing shape; none = whole-slide comment). A comment made from a text selection also remembers the selected text. |
| Resolved flag in `commentsExtended.xml` | Modern comments have `status="resolved"`; legacy comments have no resolved flag at all, so the app stores it in a private extension on the comment (see below). |
| Heading numbers give `Ref #` | `Ref #` is the slide ("Slide 3"). |

## How it works

`.pptx` is a zip of OOXML parts. The backend manipulates the slide XML
directly with `lxml` -- only parts it actually changes are re-serialized, so
masters, layouts, themes, media, charts, etc. round-trip **byte-for-byte**
(`test_save_without_changes_keeps_every_part_byte_identical`).

- **`backend/app/pptx/ooxml.py`** -- loads/saves the package, lazily parses
  parts into live trees with dirty tracking, resolves relationships, and
  creates parts/relationships/content-type overrides on demand.
- **`backend/app/pptx/parser.py`** -- walks each slide into a JSON model of
  shapes (text boxes, tables, pictures, lines, group-flattened) with
  **inheritance resolved**: PowerPoint stores position, font size, bold,
  color, alignment and bullets on layouts/masters/presentation defaults, so
  the parser follows slide placeholder -> layout -> master -> master
  `txStyles` -> `defaultTextStyle`, plus theme colors (with luminance
  modifiers), autofit font scaling, group transforms and shape-style font
  colors. The browser then renders plain absolutely-positioned boxes.
  IDs are positional paths recomputed on every parse: slide `s2`, shape
  `s2.sh7` (7 = the shape's own `cNvPr` id), paragraph `s2.sh7.p0`
  (table cell `s2.sh7.r1.c0.p0`), run `s2.sh7.p0.r3`. Also extracts slide
  size, background, notes, and layout name.
- **`backend/app/pptx/comments.py`** -- reads **both** comment formats and
  writes the legacy one. *Legacy* (`ppt/comments/commentN.xml` +
  `commentAuthors.xml`, readable by every PowerPoint version): threaded via
  `p15:threadingInfo`. *Modern* (Microsoft 365, `modernComment_*.xml` +
  `authors.xml`): nested `replyLst`, `status="resolved"`, `ac:spMk` shape
  anchor. New comments and replies on legacy comments are written legacy;
  replies/resolve on a comment that already lives in a modern part stay
  modern. What legacy comments can't express (which shape, the selected
  text, resolved, "this is an edit record") goes in a private `p:ext`
  (`pdev:state`) on the comment -- PowerPoint ignores unknown extensions, and
  the file stays self-contained, with no sidecar database.
- **`backend/app/pptx/writer.py`** -- replace a selected text range (splits
  across runs; the first affected run's formatting carries the new text, as
  PowerPoint does when you type over a selection), add a comment on a
  selection / shape / slide, reply, resolve, and replace a comment's
  stored selection (used by AI edits).
- **`backend/app/pptx/anchor.py`** -- resolves a verbatim text quote to
  run ids + character offsets (`locate_quote_in_shape`), so the AI never
  needs to know about run ids.
- **`backend/app/pptx/markdown_render.py`** -- one Markdown chunk per slide
  (`## Slide 3: Title`, bullets, tables as Markdown tables, pictures as
  `[Picture: ...]`, speaker notes as a quote block), comment anchors as
  CriticMarkup `{==text==}{>>comment:ID<<}`; plus Ref #/Para # derivation.
- **`backend/app/ai/assistant.py`** -- sends a reviewer comment plus its
  slide(s) to Claude with a forced tool call: `edit` (verbatim
  `original_text` -> `replacement_text`), `reply`, or `no_change` (flagged
  for a human).
- **`backend/app/storage/store.py`** -- the same pure JSON-file store as the
  Word version: `meta.json` per document plus a self-healing `index.json`,
  append-only `.jsonl` audit/AI logs, atomic writes with `flock`.
- **`backend/app/api/`** -- FastAPI routes; every mutating endpoint returns
  the fresh JSON model.
- **`frontend/`** -- React + TypeScript. A first-run name gate (stored in
  `localStorage`) whose value is the `author` on every comment/reply/edit;
  upload; the slide viewer; a comments sidebar (threads, "Ask AI", slide
  chips, selected-text quotes, a collapsible "Text edits" list); a
  drag-resizable comments panel; Review / Adjudicate modes; export;
  responsive down to phone width. The documents panel footer shows the
  build time Vite bakes in ("Deployed ...").

### View modes

All three render from the same model:

- **Slides** (default) -- every slide as a faithful, scalable render:
  absolutely-positioned shapes inside a box that keeps the slide's aspect
  ratio, with every length in percentages / `cqw` (1% of the slide's own
  width, via CSS container queries), so it scales to any width with no
  JavaScript layout. Layout/master decorative shapes are drawn beneath.
  Commented shapes get a dashed outline and numbered **comment pins**
  at their original position; clicking a pin or shape selects the comment.
  Each slide has a **💬 Comment on slide** button and collapsible speaker
  notes. **Selecting text** pops up **Add Comment** / **Change Text**
  (selection -> run ids + offsets, so it works mid-word and across runs of
  one paragraph, including inside table cells).
- **Slide Sorter** -- thumbnail grid (same renderer, inert) with open-comment
  badges; click a slide to jump to it.
- **Outline** -- collapsible per-slide text tree like PowerPoint's Outline
  view; click to jump. Read/navigate only.

### Review vs. Adjudicate mode

- **Review** -- the slide viewer plus comments sidebar, and **✨ AI Review**
  (`POST /api/documents/{id}/ai-review`): Claude reads the deck slide by
  slide and adds its own comments, each attached to a verbatim quote that is
  located back to an exact run (`locate_quote_in_slide`); a quote that
  doesn't match is dropped, not guessed.
- **Adjudicate** -- every open (unresolved, top-level, non-edit-record)
  comment as a card in deck order: the comment, the commented shape's text
  with the selection highlighted, a **slide thumbnail with the shape
  highlighted**, an editable AI-proposed resolution
  (`POST .../suggest-adjudications` is a read-only pass; each card's
  **Apply** is a separate call, `.../apply-adjudication`, so a human always
  reviews before anything is written), independent **Reply** / **Resolve**
  controls, the formal decision form, and a collapsible per-comment AI chat.
  For an AI `edit`, the card shows the exact text being replaced: fixed when
  the reviewer selected text, otherwise an **editable field** pre-filled with
  the AI's proposed `original_text` (PowerPoint comments attach to a whole
  shape unless text was selected, so the AI must say *which* words).
  Clicking a comment's text opens the **comment source drawer** showing that
  comment's slide.

### Comment Resolution Matrix, XLSX round trip, AI chat, persistence

These work as in the Word version (see that README for the long form):

- Each Adjudicate card has a decision (**Accept / Reject / Info Only /
  Defer**) with a required rationale and an optional manual **Ref #**,
  stored in `decisions.json` (+ append-only `decisions.jsonl`); the meta bar
  sets **Document ref** / **Rev**. **Export Comment Resolution Matrix
  (TSV)** (`GET .../comments/export`) writes one row per top-level comment
  (replies and automatic edit records are excluded) with the template's own
  header wording plus a hidden `Comment ID` column.
- **Import Filled Matrix (.xlsx)** (`POST .../comments/import-decisions`)
  finds the header row by scanning, matches rows by hidden Comment ID then
  exact comment text, saves the decision, and pushes it into the actual
  `.pptx` as a threaded reply (`"Accept: <rationale>"`) plus resolved. A row
  matching no comment **creates a new one** (author `CRM Import`) anchored
  via `Para #` (a requirement ID found in a shape's text) or `Ref #`
  ("Slide N" or just `N` -> that slide's title), else it's skipped and
  reported; skips are grouped by reason.
  `backend/tests/fixtures/crm_sample_from_user.xlsx` is the same real
  reviewer-issued sample the Word version uses.
- **Ref # / Para #** are best-effort: Ref # is the comment's slide; Para # is
  a requirement-ID-looking token (`ACA-HRS-0190`, `SSS-00340.021`) in the
  commented shape's own text, else this app's internal `slideN:shape`
  reference. They're shown as "Detected from document" hints and prefill the
  decision form.
- **Per-comment AI chat** (`POST .../comments/{id}/chat`) keeps a persisted
  transcript per comment in `comment_chats.json`; replies are plain prose
  only so they paste cleanly elsewhere.
- Everything is persisted server-side under `PPTX_DEV_DATA_DIR`; the
  frontend also remembers the open document, view mode, app mode, and
  comments-panel width across refreshes.

### Diagnosing a real deck without ever seeing it

`GET /api/documents/{id}/debug` returns structural-only diagnostics -- zip
part names, per-slide relationship types/targets, shape and table counts,
which comment parts exist, and the parsed comment count. No slide or
comment *text* is ever included, so it's safe to paste back verbatim even
from a CUI deck.

## Connecting to your own Claude API or work gateway

Open **⚙ Settings** and fill in, top to bottom:

1. **API key / auth token** -- your Anthropic API key, or the token your
   organization issued for its Claude gateway.
2. **API base URL** -- leave blank for `api.anthropic.com`. For a work gateway
   enter its address, **without** the trailing `/v1` (the app appends
   `/v1/messages`). A path prefix is kept: `https://gw.example.com/anthropic`
   is called as `https://gw.example.com/anthropic/v1/messages`.
3. **Authentication** -- how the token is sent:
   - *API key (x-api-key)* -- what api.anthropic.com expects (default).
   - *Bearer token (Authorization)* -- what most corporate, Bedrock-fronting
     and LiteLLM-style gateways expect. **If Test Connection reports HTTP 401
     with the default, switch to this.**
   - *Both headers* -- for the occasional gateway that checks both.
4. **Extra headers** (optional) -- for gateways that also want a tenant,
   subscription or proxy header: one `Name: value` per line (or a JSON object).
   Only the header *names* are ever shown back; values are write-only.
5. **Model** -- the model id **your gateway** serves. Bedrock-style gateways
   use ids like `anthropic.claude-sonnet-4-5-20250929-v1:0`, not the public
   API's short names. A 404 from Test Connection usually means this (or the
   base URL).
6. **Test Connection** sends one tiny real request and reports success, or the
   exact request URL, HTTP status, the gateway's own error text, and the most
   likely cause. Fix the setting it points at and test again.

### Importing settings from a file (optional)

Instead of typing on a phone, you can keep a small settings file on your own
device and pick it with **Import from file…** in Settings. Start from
`samples/ai-settings.example.env`: copy it to your device, fill in *your*
values, and give it an ordinary name such as `ai-settings.env` (some Android
file pickers hide dot-files; `.json` and `.txt` work too).

- It is read **in your browser only**. The file is never uploaded, and the app
  never searches your device -- it can read only the one file you choose.
- It only **fills in the form**. Nothing is saved until you review the values
  and press **Save on this device**, which stores them exactly as if you had
  typed them (see below).
- Accepted: `.env` lines (`ANTHROPIC_API_KEY=...`, `ANTHROPIC_AUTH_TOKEN=...`
  -- which also selects Bearer mode -- `ANTHROPIC_BASE_URL`,
  `PPTX_DEV_AUTH_MODE`, `PPTX_DEV_EXTRA_HEADERS`, `PPTX_DEV_AI_MODEL`), or a
  JSON object with the same names, camelCase names (`apiKey`, `baseUrl`,
  `authMode`, `extraHeaders`, `model`), or Claude Code's `{"env": {...}}` form.
  Unknown names are ignored.
- The file itself is just a plaintext secret on your device: keep it somewhere
  private and never commit it (the repo's `.gitignore` excludes `.env`).

### Where your key and URL are stored

**Only in the browser on the device you typed them into.** The server never
stores your API key/token, base URL, authentication mode, extra headers or
model -- there is deliberately no "save settings" endpoint.

| | |
| --- | --- |
| On your device | In this browser's storage (`localStorage`, or `sessionStorage` if you untick **Remember on this device**, which forgets them when the tab closes). Not encrypted, so anyone with access to that browser profile can read them. **Forget all AI settings** erases them. |
| Sent to the server | Only on the few requests that actually call the AI (Ask AI, Analyze All, AI Review, chat, Test Connection), as `x-ai-*` request headers over HTTPS. Uploads, comments, exports, etc. never carry them. |
| On the server | Held in memory for the duration of that one request, used to call your gateway, then discarded. Never written to disk or the document, never kept in a global, never in the audit logs, and scrubbed from error messages (even if a gateway echoes your token back). Another device or browser cannot use your settings. |
| Honest limit | AI calls are made *by the server*, so your token does pass through the server's memory (and, on Render, its HTTPS proxy) every time you use an AI feature. "Never stored" is the guarantee; "never leaves your device" is not possible with server-side AI. Removing the server from that path would mean calling your gateway directly from the browser, which needs your gateway to allow cross-origin browser requests and a significant rewrite -- say so if you want that. |

Each save takes effect immediately, with no restart. If you use the
environment variables below instead, those values live on the server (Render's
dashboard / the container's `.env`) -- the opposite of device-only -- so leave
them unset if you want the guarantee above.

**Environment variables** are an optional server-side alternative for a shared,
operator-managed key (the token is then stored by whoever hosts the app, and
anyone who can reach the app can use it): on Render add them under
*Environment*; in the container put them in `.env`. A value entered in the
browser always overrides the matching variable for that request.

| Variable | Meaning |
| --- | --- |
| `ANTHROPIC_API_KEY` | key or token (alias: `ANTHROPIC_AUTH_TOKEN`, which also defaults the mode to Bearer, as in Claude Code) |
| `ANTHROPIC_BASE_URL` | gateway address, no trailing `/v1` |
| `PPTX_DEV_AUTH_MODE` | `api_key` (default), `bearer`, or `both` |
| `PPTX_DEV_EXTRA_HEADERS` | `Name: value` lines (use `\n` between them in a one-line env var) or a JSON object |
| `PPTX_DEV_AI_MODEL` | model id |

Not supported: calling AWS Bedrock's own runtime API directly (SigV4 signing);
that needs a gateway that speaks the Anthropic Messages API, or a different
client.

## Local container deployment (single-user desktop, CUI-capable)

For running on your own machine -- including one approved for CUI -- so
documents never leave it. The only outbound connection the app makes is the
one you configure for AI features (the Anthropic API or your own
Anthropic-compatible gateway); with no key set it makes none, and every
non-AI feature works fully offline. There is no telemetry.

**Requirements:** Docker Desktop / Docker Engine with Compose v2, or Podman
with `podman compose`. No Python or Node needed on the host.

```bash
cp .env.example .env          # edit if you want (all settings are optional)
docker compose up -d --build
# open http://localhost:8000
```

Upload `samples/sample.pptx` to try it. Stop with `docker compose down` (your
data is kept); `docker compose logs -f` to watch; `docker compose ps` shows
the health status.

### What the container does for you

- **Loopback only.** The port is published on `127.0.0.1`, so only this
  computer can reach it. **The app has no login** -- anything that can reach
  the port can read and edit every uploaded deck. Only change
  `PPTX_DEV_BIND` (in `.env`) to a LAN address if an authenticating reverse
  proxy sits in front.
- **Least privilege.** Runs as an unprivileged user (uid 10001) with a
  read-only root filesystem, all Linux capabilities dropped,
  `no-new-privileges`, and a PID limit. The only writable places are the
  data volume and `/tmp`.
- **No CORS.** The UI and API are the same origin, so cross-origin access is
  disabled (`PPTX_DEV_CORS_ORIGINS=""`); other web pages open in your browser
  cannot call the API.
- **Persistent data** in a named volume mounted at `/data`: uploaded decks
  (original + working copy), comments/decisions, AI chat transcripts, and the
  edit/AI audit logs. It survives `down`, rebuilds, and image upgrades. To
  start completely fresh: `docker compose down -v` (**this deletes all data**).
- **Healthcheck** against `/api/health` (`docker compose ps` shows
  `healthy`). The response also reports `dataDirIsMountPoint: true`, confirming
  data really is on the volume.
- **Stateless AI settings.** Anything entered in the Settings modal stays in
  the browser and is sent only with AI requests; the container stores none of
  it (see "Where your key and URL are stored").

### Configuring AI

Two ways; pick one:

1. **In the app (default):** open the gear (Settings) modal and enter your
   key/token, base URL, authentication mode and model. They are kept only in
   that browser on that device and sent with each AI request; the container
   never stores them. See "Connecting to your own Claude API or work gateway".
2. **Environment (shared, operator-managed):** put `ANTHROPIC_API_KEY=...` (and
   the other variables in `.env.example`) in `.env` and restart. The key then
   lives on the host and in the container's environment for everyone who can
   reach the app. Fine for a single-user desktop; leave blank to use option 1.

The Settings modal's **Test Connection** button confirms the configuration works
before you rely on it.

### Backup and restore

```bash
# backup the data volume to ./pptx-data.tgz
docker run --rm -v pptx-review-ai_pptx-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/pptx-data.tgz -C /data .
# restore into a (new, empty) volume
docker run --rm -v pptx-review-ai_pptx-data:/data -v "$PWD":/backup alpine \
  tar xzf /backup/pptx-data.tgz -C /data
```
Keep backups to the same standard as the documents themselves. (On Windows
PowerShell use `${PWD}` instead of `"$PWD"`.)

### Using a folder instead of a named volume

Edit `docker-compose.yml`: replace `pptx-data:/data` with `./data:/data`, and
on Linux make it writable for the container's user first:
`mkdir data && sudo chown 10001:10001 data`. Prefer the named volume on
Windows/macOS: the store relies on atomic renames and file locking, which
Docker Desktop's bind-mount file sharing may not provide reliably.

### Building without internet access to the build host / moving the image

Build once on a connected machine, then carry the image over:
```bash
docker compose build
docker save pptx-review-ai:local | gzip > pptx-review-ai.tar.gz
# on the target machine (with docker-compose.yml and .env alongside):
gunzip -c pptx-review-ai.tar.gz | docker load
docker compose up -d --no-build
```
The image contains no secrets (keys come from `.env` at run time).

### Networks that inspect TLS

If `docker compose build` fails with `CERTIFICATE_VERIFY_FAILED` (a corporate
proxy re-signing HTTPS), point the build at your organization's CA bundle in
PEM format via `PPTX_DEV_CA_BUNDLE` in `.env` (or the shell). It is passed as
a BuildKit secret for `npm` and `pip` only -- it is not stored in the image.
Registry/proxy settings for Docker itself (pulling `node` and `python`) are
configured in Docker, not here.

### Updating

```bash
git pull
docker compose up -d --build     # data volume is untouched
```
Pin base images by digest in the `Dockerfile` if your change-control process
requires reproducible rebuilds.

### Verified behavior

Built and run with Docker 29 / Compose v5: container reports healthy, runs as
uid 10001, root filesystem is read-only, the port binds to 127.0.0.1 only, no
CORS headers are sent, an uploaded deck survives `docker compose down` /
`up`, and a root-owned data directory (the Render disk case) is repaired and
served as the unprivileged user. Not covered: Podman, Windows/macOS hosts, and
any specific accreditation requirements -- review the settings above against
your own.

## Deployment (Render — demo/staging only, non-CUI data)

The repo root `Dockerfile` builds the whole app as one container: a Node
stage builds the React frontend, then a Python stage installs the backend
and serves the built frontend's static files from the same FastAPI process
(`PPTX_DEV_FRONTEND_DIST`, wired up in `app/main.py`) — so there's one
service, one URL, same-origin requests, no CORS or reverse-proxy setup.

**`render.yaml`** is a Render Blueprint that deploys it:

1. Push this repo to GitHub (already done) and in Render, **New → Blueprint**,
   pointing at this repo. Render reads `render.yaml` and creates the service.
2. The blueprint requests a **paid `starter` plan with a 1GB persistent
   disk** mounted at `/data` (`PPTX_DEV_DATA_DIR=/data`). This is required:
   Render's **free plan has an ephemeral filesystem**, so every deploy or
   restart would silently wipe every uploaded document. Don't move this to
   the free plan without also moving the data directory to something
   persistent. If this service already existed *before* the `disk:` block
   was added to `render.yaml`, a blueprint sync doesn't always retroactively
   attach a disk to it — check the service's **Disks** tab in the Render
   dashboard once and confirm a disk is actually mounted at `/data`; if not,
   add one there (or recreate the service from the blueprint).

   **To check this yourself without the dashboard**, hit
   `GET /api/health` on the deployed URL (`curl
   https://<service>.onrender.com/api/health`). It returns
   `dataDirIsMountPoint` (`true` only if `/data` is a real mounted disk --
   `false` means it's just an ordinary directory in the container's own
   ephemeral filesystem, wiped on every restart) and `serverStartedAt` (the
   process's own boot time). If uploaded documents ever appear to vanish,
   compare `serverStartedAt` across two requests a few minutes apart: a
   jump to a recent time means the container restarted in between (a
   redeploy, a crash, or -- on a non-`starter` plan -- an idle spin-down),
   which is the actual cause if `dataDirIsMountPoint` is also `false`; if
   `dataDirIsMountPoint` is `true` and documents still vanish, that would
   be a real application bug worth reporting, not a plan/disk mismatch.
3. Once deployed, Render gives you a `https://<service>.onrender.com` URL —
   open it directly; there's no separate frontend URL/build to manage.

**No `ANTHROPIC_API_KEY` (or `ANTHROPIC_BASE_URL`) is set in this deployment
on purpose** -- `render.yaml` doesn't declare either one. Each user enters
their own key/token and base URL in the ⚙ Settings modal; they stay in that
user's browser and are sent only with AI requests (see "Where your key and URL
are stored"). Nothing is saved on Render, so a restart, redeploy or spin-down
loses nothing and there is no secret to rotate on the server. If you instead
want a shared key for everyone who can reach the URL, add `ANTHROPIC_API_KEY`
as an env var in the Render dashboard's Environment tab yourself -- but then
anyone who can reach the URL can use it, and it is stored by Render.

To build and run it locally the same way Render will:
```bash
docker build -t pptx-dev .
docker run -p 8000:8000 -v pptx-data:/data pptx-dev   # see the previous section for the hardened docker compose setup
# open http://localhost:8000, then set your API key via the Settings modal
# -- or pass -e ANTHROPIC_API_KEY=sk-... to bake one in instead
```

**Important:** Render is a public commercial PaaS, not FedRAMP/GovCloud
authorized. Use it for demos and testing with sample (non-CUI) documents
only. For real CUI-bound documents, use the AWS GovCloud deployment below —
the app's storage layer (pure JSON files, no S3, no SQL server) was
specifically designed to move between the two without changes: same
Dockerfile, same `PPTX_DEV_DATA_DIR` env var, just pointed at an EFS mount
instead of a Render disk.

## Deployment (AWS GovCloud, containerized, no S3/SQL server)

All persistent state — uploaded `.pptx` files and the JSON/JSONL store
described above — lives under `PPTX_DEV_DATA_DIR` (defaults to `./data`).
For a containerized deployment:

- Mount that directory on **Amazon EFS** (available in GovCloud regions,
  POSIX filesystem over NFSv4.1, which supports the atomic rename and
  `flock()` locking this store relies on). No S3, no RDS/SQL Server to
  provision or get into an ATO boundary — just a filesystem mount.
- Point `PPTX_DEV_DATA_DIR` at that mount via an environment variable in
  the task/pod definition (ECS Fargate or EKS both work).
- Multiple backend replicas can safely share the same EFS mount — every
  write in `store.py` is atomic and lock-guarded per document (and
  separately for the shared `index.json`), so concurrent requests across
  replicas can't corrupt or interleave writes.
- If `index.json` is ever lost or corrupted, `DocumentStore.rebuild_index()`
  (also called automatically on startup if it's missing) regenerates it by
  scanning every document's `meta.json`, which is the actual source of
  truth per document.
- Set `ANTHROPIC_API_KEY` as a secret (e.g. via the container's secrets
  manager of choice) rather than a plain env var where your ATO requires it.
- If the public Anthropic API isn't reachable from your CUI network but an
  internal gateway in front of AWS Bedrock is (one that speaks the same
  Anthropic Messages API — most Bedrock access-gateway setups do), set
  `ANTHROPIC_BASE_URL` to that gateway's URL alongside `ANTHROPIC_API_KEY`
  (whatever bearer token the gateway expects) and, if Bedrock's model IDs
  differ from the direct-API ones, `PPTX_DEV_AI_MODEL` to match. Give
  `ANTHROPIC_BASE_URL` just the host, e.g. `https://gateway.example.mil`,
  **not** `https://gateway.example.mil/v1` — the Anthropic SDK always
  requests `/v1/messages` itself, so a base URL that already ends in `/v1`
  produces a `/v1/v1/messages` 404 against a real gateway (this is a
  natural mistake since several other OpenAI/Anthropic-compatible tools
  *do* want `/v1` included; `config.normalize_base_url()` strips a trailing
  `/v1` either way, so getting this wrong is harmless). Users can also
  enter them in the webapp's Settings modal (⚙); those stay in the user's
  browser and are sent per AI request (see `backend/app/ai/credentials.py`),
  never stored server-side. For a shared deployment where the
  organization holds the key, inject them as env vars via your container
  platform's secrets manager instead. This only works for a gateway
  that's already Anthropic-API-compatible — calling Bedrock's own runtime
  endpoint directly (different request/response shape, AWS SigV4 or
  Bedrock's native API-key auth) would need the Anthropic SDK's separate
  `AnthropicBedrock` client instead, which isn't wired up here.
- The Settings modal's **Test Connection** button sends one minimal real
  request (`max_tokens=1`) using the key/base URL/model currently in the
  form (saved or not) — the exact same client construction "Ask AI" uses —
  and reports the model, base URL, and round-trip latency on success, or
  the real error otherwise (`POST /api/settings/anthropic-key/test`).
  Point of this over just clicking "Ask AI" on a real comment: it's free
  of side effects (nothing gets written to the document) and gives you a
  definite yes/no before you start relying on it. A "Bedrock's own runtime
  endpoint" wiring gap would show up here as clearly as anywhere else --
  e.g. an "Invalid model name... call `/v1/models` to view available
  models for your key" error means the base URL/key reached a real
  gateway fine, but the model ID needs to be set to whatever your
  gateway's Bedrock-style ID is instead of the direct API's short name.

## Known limitations / next steps

- **Not yet verified in real PowerPoint.** The reader is tested against
  comment XML written by hand the way PowerPoint writes it, and exports are
  checked by re-parsing and by opening them with python-pptx -- but there has
  been no round trip through Microsoft PowerPoint itself. In particular:
  *new* comments are written in the legacy format, which current PowerPoint
  365 opens but may show as legacy comments; the legacy "resolved" state and
  edit-record flag live in a private extension PowerPoint ignores (and may
  drop if it re-saves the file, at which point those comments simply read as
  open); and modern-format replies/resolve are written to the documented
  schema without an Office instance to confirm them.
- **The slide render is a faithful preview, not PowerPoint's engine.** It
  models placeholder/theme inheritance, fills, outlines, tables, pictures,
  lines, rotation and group transforms. It does not model: custom fonts,
  gradient/picture fills, shadows/effects, table *styles* (a colored header
  row is approximated), SmartArt/charts/embedded objects (shown as a labeled
  placeholder), pictures that live on layouts/masters, or text-fit
  recalculation. Text always round-trips untouched regardless of how the
  preview looks.
- Text edits operate within **one paragraph** (selections can span runs, not
  paragraphs, line breaks, or fields). Pictures, charts and layout can't be
  edited in the UI; the AI is told to reply instead of editing for those.
- A comment attached to a *whole shape* has no stored selection, so an AI
  edit needs the AI-proposed `original_text` to locate the words to replace
  (and fails cleanly, changing nothing, if it isn't found verbatim).
- Comment positions: foreign comments are mapped to the smallest shape
  containing their position; a comment that sits over empty space is treated
  as slide-level.
- Slide text is not searchable across decks and there is no slide
  add/delete/reorder.
- AI adjudication sends the whole deck's Markdown when it is under ~60k
  characters, otherwise only the comment's own slide.
- No authentication/authorization yet -- anyone who can reach the API can
  read/edit/export any document. The storage layer is safe under concurrent
  requests (see Deployment), but there's no per-user identity or access
  control in front of it.
- The JSON-file store trades away cross-document queries for zero
  infrastructure dependencies. Fine at this app's expected scale; if that
  ever becomes a bottleneck, `store.py` is a small, isolated module to swap
  for a managed NoSQL backend (e.g. DynamoDB, available in GovCloud without
  needing S3 or a SQL server either).
